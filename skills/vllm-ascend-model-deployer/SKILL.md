# vLLM Ascend 模型服务部署

交付一个 SSH 断开后仍在运行、通过真实推理请求验收的服务。以具体模型、硬件和部署方式对应的官方示例为基线，在指定工作目录交付可重复执行的步骤。

## 先给用户核对

接受一句话调用，例如 `$vllm-ascend-model-deployer 帮我在 192.0.2.10 上拉起 DeepSeek-V4.1-Flash，权重位于 /mnt/weights/DeepSeek-V4.1-Flash-1017-w4a8。` 也接受逐项指定配置。先提取用户给出的主机（IP、主机名或 SSH 别名）、模型和权重路径，再按本次请求的语义、上下文和官方教程补齐计划。用户明确给出的值优先。

- **部署方式。** 只给一台服务器、没有提到 P/D 分离，且模型教程提供单节点共置示例时，优先提议“单节点共置”，标注依据。出现“PD 分离”“1P1D”或明确的 prefill/decode 角色时，按对应拓扑规划；仅给出多台机器时，结合角色描述和教程提出候选，并列明需要确认的分工。P/D 分离与节点数量是两个维度，一台服务器也可能要求 P/D 分离。
- **容器和路径。** 缺省时，用模型名拟定 Docker 容器名（如 `deepseek-v4-1-flash`），优先沿用用户在本次请求中给出的工作区约定。没有约定时可提议 `/mnt/share/<容器名>`，标注挂载、可写性和重名情况待上机检查。额外适配点缺省为“无”，并行度、端口及服务别名取对应官方示例。
- **现场事实。** 模型名或权重目录名可以提示教程和量化格式。硬件型号、实际卡数、剩余显存及目录内容需要证据。若硬件未知，核对单列出适用的条件分支，例如“若为 A3 采用 A3 镜像及章节，若为 A5 采用 A5 镜像及章节，执行后先探测”。若探测结果与已确认的分支相符，直接继续；若需要新增节点或改变已确认的拓扑，先提交调整方案。

按本次部署的区域和硬件型号选择镜像。用户显式给出镜像名时优先采用。区域未说明时，沿用绿区作为待确认的默认候选；硬件未知时列出该区域的 A3/A5 两种命令。核对单中写明区域及完整的 `docker pull <镜像名>` 命令。

**首轮直接给出核对单和简短执行计划，等用户确认后才连接服务器。** 用“已给出 / 推断（理由）/ 默认 / 待探测”标明每项来源。核对单涵盖主机与 SSH 用户、硬件、模型与权重、容器和工作目录、部署拓扑与设备需求、镜像和源码策略、官方章节、端口、挂载及额外适配。若缺少无法推断且会阻止执行的信息（例如指定跨机 1P1D 却缺第二台地址），在计划末尾只问这一类缺口。对于可在授权后探测的事项，直接给出条件计划。

计划按“探测硬件与资源 → 复用或拉取镜像 → 创建容器、核对版本 → 按需适配 → 拉起并验收”展开。请用户回复“确认”“执行”或指出修改。首条请求里的“帮我拉起”触发规划；对所列计划的明确同意即可执行。只收到修正时，更新受影响的配置和步骤供确认；若用户说“改为……并执行”且所需信息已齐全，按修正后的方案继续。公开教程和版本可以在规划阶段查询。若没有匹配的官方示例，指出缺口并请用户确认替代基线。历史任务中的机器和释放设备的授权只属于原任务。

## 收到执行指令后

1. **核对现场。** 在宿主机确认硬件、逻辑 NPU、Docker runtime、磁盘、镜像缓存、同名容器、权重和工作目录挂载、服务端口及设备占用。已有同名容器时核对镜像、挂载和实际服务；一致且已健康时直接验收，有冲突则保留原容器并报告。多节点逐台核对官方要求的角色、设备和互联条件。
2. **创建容器。** 从教程对应的 `docker run` 复制实际需要的命令，保存为 `<工作目录>/scripts/create_container.sh`。保留官网的网络、IPC、设备分配和驱动挂载，代入已确认的镜像、容器名和路径。在目标宿主机将完整镜像名赋给 `IMAGE`，先用 `docker image inspect "$IMAGE"` 检查缓存，缺失时才执行 `docker pull "$IMAGE"`。检查容器内能读到权重、能写工作目录。若设备已被独占，先验证当前可查的映射，把设备运行验证留到交接后。
3. **对齐运行环境。** 宿主机仅承担 Docker、挂载、资源归属查询等必要操作；源码准备、构建、安装、服务启动、调试和功能验证均在指定容器内完成。在容器中比对镜像自带的两份实际提交与目标 SHA；nightly 标签本身不能证明匹配。匹配则复用，否则按对应仓库的官方安装方式对齐，只安装需要的部分。若指定提交缺少配对文件或无法解析其中的版本，报告版本缺口，请用户指定可用配对。核对最终 Python 导入路径及对应源码提交。确需安装时可另存一次性 `scripts/prepare_source.sh`，日常拉起服务不重复安装。
4. **管理下载归档。** 镜像直接 pull 或源码直接 clone 时无需另造压缩包。若使用离线镜像归档，先校验并 `docker load`，确认目标镜像 ID 和架构；源码压缩包在解压后核对提交或校验和及目录完整性。所有依赖该副本的节点导入或解压成功后，删除本次下载的相应归档、已合并的下载分块和中转副本，核实已移除。保留已导入镜像与已解压源码，避免按通配符清理共享目录中他人的文件。
5. **按官网生成服务脚本。** 将选定教程的服务命令保存为 `<工作目录>/scripts/start_service.sh`。保留环境变量、启动入口和原有参数，替换实际路径及用户要求的改动。逐项与官网对照，仅加入所选拓扑必需的联动改动，或由现场报错证实的适配。教程使用 `vllm serve` 时直接使用该入口。若通过 `docker exec` 拉起，核对镜像入口实际设置的运行环境，按需补齐。准备好容器内后台启动命令和日志路径，或沿用教程的常驻启动方式。
6. **先解决设备交接，再启动。** 一旦发现可用 NPU 或显存不足，继续完成镜像、创建容器、源码、脚本和其他不占用这些设备的准备。准备完毕后，报告所在节点、设备编号、所需及可用显存、占用容器名/ID、进程或服务、已完成事项，然后等待用户协调或指令。AICore 为零仍可能存在常驻权重或设备独占。只有用户明确授权释放时才处理对应对象；若实际还需下线其他入口或额外容器，先说明新增影响并等待指令。设备原本可用或已按指令完成交接时，核对设备、显存和端口，立即在指定容器中启动并保留服务，使 SSH 退出后仍可访问。
7. **验收并留下复现记录。** 跟踪初始化日志直到服务就绪或出现具体错误。服务就绪后，在容器内用 `curl` 检查 `/health` 和 `/v1/models`，核对已部署的模型别名，再发一次真实推理请求。对话模型用下方示例核对最终回答；若用户给了测试问题和预期答案，优先用用户的用例。纯文本补全模型用 `/v1/completions` 核对 `choices[0].text`，嵌入模型用 `/v1/embeddings` 检查返回的向量及维度。确认服务在启动会话退出后仍健康。在 `<工作目录>/README.md` 简要记录官方章节、镜像 ID、两份实际 SHA、挂载与拓扑、创建/一次性安装/启动/验证命令、日志位置、偏离官网的原因、归档清理，以及 curl 测试的输入、预期与实际结果。遇到阻塞时记录失败阶段和日志，给出需要用户协调的具体事项。

### 对话模型的 curl 验收

在容器里使用实际服务入口和已核对的模型别名替换下例中的 `BASE_URL` 和 `example-chat`。P/D 分离部署通过服务对外的统一入口发请求。若该模型的官方示例需要额外的请求参数，沿用其设置。

```bash
BASE_URL=http://127.0.0.1:8000
curl -fsS --max-time 300 "$BASE_URL/v1/chat/completions" \
  -H 'Content-Type: application/json' \
  -d '{"model":"example-chat","messages":[{"role":"user","content":"1 + 1 等于几？只回答一个数字。"}],"temperature":0,"stream":false}' |
  python3 -c 'import json, sys; answer = json.load(sys.stdin)["choices"][0]["message"]["content"]; print("模型回答:", repr(answer)); sys.exit(0 if isinstance(answer, str) and answer.strip() == "2" else "验收失败：预期最终回答为 2")'
```

收到预期正文才判定推理验收通过。若 HTTP 报错、只有推理过程、正文为空或答案不符，记录实际响应并查看服务日志，修正后重测。

在现场遇到 runtime 注入失败、设备仍被旧容器独占，或 DeepSeek TP8PP2 配置及锁页内存错误时，按现象查阅[条件适配记录](references/ascend-deployment.md)。每次只改变能解释当前问题的配置，再用同一验收方式复测。
