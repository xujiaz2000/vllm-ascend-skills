# vLLM Ascend profiling

例如 `$vllm-ascend-profiler 通过 /srv/model/start_service.sh 拉起模型服务，采集 1s 的 profiling`。

## 先列出采集计划

从调用者给出的脚本和当前会话提取参数。把计划列给调用者，注明每项是已指定、建议值还是待现场核实：

1. **服务**：目标主机、启动脚本、模型别名、容器或进程、API 地址、并行拓扑；已有服务是否需要重启，重启会影响哪个入口。
2. **负载与窗口**：压测工具、数据集、并发、输出长度、warmup、按什么事件触发、持续多久。只有脚本和时长时，建议 AISBench + AIME 2026、流式对话、并发 1、1 次 warmup、8 道正式题完成且下一题已接入时采样。输出长度沿用模型测试配置并列出实际值。调用者给出的负载或触发条件优先。
3. **产物与验收**：写出服务进程可见的采集路径及对应宿主机路径。默认用工作目录下的 `profiling/<本次运行标识>/`，每次使用新目录；说明将核对哪些 worker、如何确认采样时有实际 NPU 活动，给出解析后的时间线路径。

等待调用者确认或修正。收到可以执行的修正（例如“改为 3 秒，其他照旧”）就更新计划并执行。同一轮已确认的项目无需重复询问。若修正仍有歧义，只问会改变执行对象或窗口的问题。计划确认前不改启动参数、不重启服务、不发起压测。

## 按计划采集

1. 在目标环境检查服务实际使用的启动命令、版本和输出目录挂载。确认各 worker 可写，宿主机能读。需要启用 profiler 时，仅在原有 `vllm serve` 参数中加入或合并下例配置，将路径替换为服务进程可见的本次绝对路径。保留已有模型、并行和推理参数。

   ```bash
   --profiler-config '{"profiler":"torch","torch_profiler_dir":"/work/profiling/run-001","torch_profiler_with_stack":false}'
   ```

2. 通过指定脚本启动或重启目标服务；若运行中的配置和输出目录已符合计划，可直接复用。等待 `/health` 成功，核对 `/v1/models` 的别名和当前版本注册的 `POST /start_profile`、`POST /stop_profile`。出现额外停机或需释放其他服务占用时，向调用者说明影响。
3. 使用 AISBench 时，按[负载与触发步骤](references/aisbench.md)准备镜像、数据和模型配置。使用其他负载时也要能区分 warmup 和正式请求。先布置观察点，再启动负载；到达约定的完成数时，确认窗口内仍有推理请求。错过窗口，记录原因，在新的测试轮次按原计划重新计数。
4. 触发时向服务根地址 POST `/start_profile`，成功后等待约定时长，再 POST `/stop_profile`。记录触发依据、两次响应状态、开始响应与发出停止请求的时间间隔。停止接口可能还要等待 worker 写盘，给它足够的超时。响应丢失时，先核对服务日志和 profiler 状态，再决定是否需要补发停止。负载和原始文件写入完成后再离线解析。

## 解析与交付

将随 skill 提供的 [profiler.py](scripts/profiler.py) 放在目标主机可挂载的位置。在与服务相同的 TorchNPU、CANN 环境中，以独立 Python 进程运行。参数是**直接包含本轮各个 `*_ascend_pt` 目录的父目录**。多节点使用独立磁盘时，在各节点解析对应的本地目录。下面以单节点 16 个全局 rank 为例，执行时按实际拓扑替换：

```bash
python3 profiler.py "$PROFILE_DIR" --ranks $(seq 0 15)
```

脚本调用 `torch_npu.profiler.profiler.analyse()`，再核对 rank 元数据、解析时间线和算子明细。若当前版本的输出格式不同，按该版本实际文件核对相同证据。worker 日志若提示 daemon 进程无法在线解析，可以用上述独立进程处理已有原始数据。解析失败优先修复解析环境并复用原始数据。

最终给出**主机名、宿主机上的解析根目录、至少一个可直接打开的 `ASCEND_PROFILER_OUTPUT/trace_view.json` 绝对路径**。列出已验证与预期的 rank、算子数据是否非空、正式请求成功/失败数、实际采集间隔，以及服务最终状态。多节点逐台列路径；有缺失则点名缺少的 rank 或文件。
